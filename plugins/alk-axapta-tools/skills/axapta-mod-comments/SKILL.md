# Axapta Modification Comments

В проектах внедрения Microsoft Dynamics AX (компания ALK / коды проектов вида `ALK_DEVAX...`) **не используется** система версионирования (нет git/TFS). Поэтому каждая модификация существующего кода и любой новый объект (класс, метод, таблица, форма, EDT, меню и т.д.) маркируется специальными комментариями. Это критически важная конвенция — без неё невозможно отследить, кто и зачем менял код.

## Когда применять навык

Применяй ВСЕГДА, когда:
- редактируешь существующий метод X++ (`.xpo`, `.xpp`)
- добавляешь новый метод, поле, член класса, таблицу, форму, ресурс
- комментируешь/выпиливаешь старый код (он остаётся в исходнике, обёрнутый в `/* ... */`)
- меняешь свойства объектов AOT
- любые другие модификации в проектах с префиксом `ALK_DEV*`

## Параметры модификации

Для маркировки нужны 5 параметров:

| Параметр | Пример |
|----------|--------|
| `<Код проекта>` | `ALK_DEVAX12` |
| `<Код модификации>` | `DAX_012234` |
| `<Описание модификации>` | `[MON] Доработать отчет по расписанию дежурств` |
| `<Текущая дата>` | формат `DD.MM.YYYY`, например `08.05.2026` |
| `<Ник пользователя>` | например `akaz` |

## Нормализация кода модификации

Код модификации принимается в любом виде (`DAX_11233`, `DAX-11233`, `DAX-0011233`, `DAX_012455`).
**Немедленно при получении** нормализовать по алгоритму:

1. Разобрать по шаблону `([A-Za-z]+)[_-]0*(\d+)` → получить `PREFIX` и целое число `N` (без ведущих нулей).
2. **Для хранения** (memory, config): `{PREFIX}-{N}` — дефис, без ведущих нулей. Пример: `DAX-12455`.
3. **Для комментариев в коде**: `{PREFIX}_{N:06d}` — подчёркивание, 6 цифр с ведущими нулями. Пример: `DAX_012455`.

| Ввод | settings / memory | В комментарии |
|------|-------------------|---------------|
| `DAX_11233` / `DAX-11233` / `DAX-0011233` | `DAX-11233` | `DAX_011233` |
| `DAX_012455` / `DAX-12455` / `DAX_12455`  | `DAX-12455` | `DAX_012455` |

**Не сохраняй** ненормализованную форму. Если в memory уже лежит `DAX_012455` (старый формат) — при следующем сохранении перезаписать на `DAX-12455`.

**Текущую дату** всегда брать из системного контекста (поле `currentDate` в системных напоминаниях), приводя к виду `DD.MM.YYYY`. Не используй относительные даты («сегодня», «вчера»).

## Сбор параметров

Перед первым проставлением комментария в сессии — если параметры неизвестны или не закреплены в memory — спроси пользователя через `AskUserQuestion`. Один вопрос на параметр (или один сводный с предзаполненными значениями из memory). Сохранённые в memory значения проекта/ника обычно стабильны между задачами — их предлагай по умолчанию. Код модификации и описание уникальны для каждой задачи — спрашивай явно.

Сразу после получения кода модификации **применить нормализацию** (см. §«Нормализация кода модификации»): хранить в canonical-settings форме (`PREFIX-N`), во всех строках комментариев использовать canonical-comment форму (`PREFIX_NNNNNN`).

После получения параметров **сразу сохрани** их в memory как `project` (текущий тикет: код в canonical-settings форме, описание, дата начала) и в `user` (ник + текущий проект ALK_DEVAX...) — чтобы не переспрашивать в той же или соседней задаче.

## Шаблоны комментариев

### 1. Однострочный — заголовок нового объекта или нового метода в **чужом** объекте

Новый класс / таблица / форма — маркер один раз на объекте:

```xpp
//ALK_DEVAX12, DAX_012234, [MON] Доработать отчет по расписанию дежурств, 08.05.2026, akaz
class SomeNewClass extends SomeBase
{
    // методы и поля этого класса — без дополнительных маркеров текущей мод
}
```

Новый метод в **чужом** (стандартном / другой мод) объекте:

```xpp
//ALK_DEVAX12, DAX_012234, [MON] Доработать отчет по расписанию дежурств, 08.05.2026, akaz
public void newMethod()
{
    // ...
}
```

Новый метод в объекте **текущей** мод (маркер уже в `classDeclaration`) — **без** этого header.

### 1a. Где живёт маркер объекта: `classDeclaration` и `_changeDeclaration`

У класса есть настоящий `classDeclaration` — маркер объекта ставится там. У таблиц
и форм такого места нет: у таблицы объявления вообще не бывает, а `classDeclaration`
формы — это служебный `public class FormRun extends ObjectRun`, куда прикладной
комментарий не относится.

**Для таблиц и форм заводится метод-«шапка» `_changeDeclaration`** (пустой,
существует только ради комментария), маркер ставится в нём:

```xpp
// CIT000, MOD-240-APP, Разработка MCP-сервера для Axapta (by AKAZ), 29.07.2026, akaz
private void _changeDeclaration()
{
}
```

Имя именно `_changeDeclaration` — не `_classDeclaration`.

**На форме `_changeDeclaration` дополнительно перечисляет элементы дизайна**,
которые модификация добавляет или меняет. Это особенно важно для чужой формы:
правки дизайна в xpo раскиданы по `CONTROL`-блокам в конце файла, и без сводки
непонятно, что именно сделала модификация.

Оформление зависит от того, **в этом ли проекте создана форма**.

**Своя форма (создана в текущей мод)** — header-маркер на месте, перечень простым
списком:

```xpp
// CIT000, MOD-240-APP, Разработка MCP-сервера для Axapta (by AKAZ), 29.07.2026, akaz
private void _changeDeclaration()
{
    // Элементы дизайна формы:
    //   Tab (ShowTabs = No)
    //     TabPage
    //       ConnectionGroup (DataGroup Connection) — адрес сервера, токен, автоподключение
}
```

**Чужая форма (создана в другом проекте)** — header-маркер **опускается**: объект
не наш, и шапка соврала бы об авторстве. Вместо неё каждое изменение оборачивается
блочными маркерами, а описание идёт между `/*` и `*/` с секциями `added:` и
`changed:` и **полными AOT-путями** элементов:

```xpp
private void _changeDeclaration()
{
    // + ALK_DEVAX12, DAX_003589, BKO. Изменение проверок в акте, 16.03.2022, Felinger -->
    /*
    added:	\Forms\ALK_ActDeviationTableList\Designs\Design\[Tab:Tab]\[TabPage:LineTabPage]\[Group:GroupLength]\StringEdit:ALK_eActDeviationTable_PickingListIdInitial

    changed:
    \Forms\ALK_ActDeviationTableList\Designs\DesignList\ALK_ActDeviationTableList
        очищено поле DataSource (был указан несуществующий источник данных)

    \Forms\ALK_ActDeviationTableList\Designs\DesignList\RetirementMsgActId
       очищено свойство PresenceDataField (было указано несуществующее значение [1])
    */
    // - ALK_DEVAX12, DAX_003589, BKO. Изменение проверок в акте, 16.03.2022, Felinger <--
}
```

Правила оформления блока:
- путь пишется целиком от `\Forms\...`, узлы дизайна — в квадратных скобках
  `[Тип:Имя]`, конечный элемент — `Тип:Имя` без скобок;
- `added:` — что добавлено, `changed:` — что изменено, с указанием **какое
  свойство и почему** (не просто «поправлено»);
- каждая модификация — свой блок `+/-`; при следующей правке той же формы
  добавляется новый блок, старые не трогаются — так в одном методе накапливается
  история изменений формы разными модификациями.

### 2. Многострочный блок — новые строки внутри **чужого** существующего метода

```xpp
    // + ALK_DEVAX12, DAX_012234, [MON] Доработать отчет по расписанию дежурств, 08.05.2026, akaz -->
    new code line 1;
    new code line 2;
    // - ALK_DEVAX12, DAX_012234, [MON] Доработать отчет по расписанию дежурств, 08.05.2026, akaz <--
```

Открывающий маркер: `// + <параметры> -->` (стрелка `-->`).
Закрывающий маркер: `// - <параметры> <--` (стрелка `<--`).

В объекте текущей мод такие блоки **не ставятся**.

### Одна строка — комментарий в конце строки, а не блок

Блок `+/-` из трёх строк ради одной строки кода — избыточен. **Если добавляется
или меняется ровно одна строка и итоговая длина (код + комментарий) не превышает
246 символов — маркер ставится в конец этой же строки**, без обрамления:

```xpp
// ПРАВИЛЬНО — одна строка, маркер в хвосте
    element.initSQLTrace();
    element.alk_initMcp(); //ALK_DEVAX12, DAX_012234, Описание, 08.05.2026, akaz

// НЕПРАВИЛЬНО — блок из трёх строк ради одной строки кода
    element.initSQLTrace();
    // + ALK_DEVAX12, DAX_012234, Описание, 08.05.2026, akaz -->
    element.alk_initMcp();
    // - ALK_DEVAX12, DAX_012234, Описание, 08.05.2026, akaz <--
```

Формат хвостового маркера: пробел, `//`, сразу параметры без пробела —
`код; //<параметры>`. Это тот же вид, что у однострочного header-маркера,
и он совпадает со стилем, уже принятым в приложении, например:

```xpp
    element.timeoutHandlerSyncState(); //CIT000, MOD-028-DEV, Отображения идущей синхронизации (by AKAZ), 07.05.2018, akaz
```

Блочные `+/-` остаются для случаев, когда:
- добавляемых/изменяемых строк **больше одной**;
- одна строка, но с маркером она вылезает за **246 символов** (тогда блок, маркеры
  по правилу §«Отступ маркеров»);
- нужно сохранить заменённый код в `/* ... */` (см. §3 и §4) — там блок обязателен
  независимо от числа строк.

### Отступ маркеров

**Маркеры выравниваются по отступу кода, который они обрамляют** — на ту же
колонку, а не к началу строки. Иначе в форме сравнения AX при импорте блок
визуально «выпадает» из структуры метода и диф читается плохо.

```xpp
// ПРАВИЛЬНО — маркеры на отступе обрамляемого кода
public void insert()
{
    this.validateSomething();

    // + ALK_DEVAX12, DAX_012234, Описание, 08.05.2026, akaz -->
    if (this.AccountNum)
    {
        this.alk_updateRelated();
    }
    // - ALK_DEVAX12, DAX_012234, Описание, 08.05.2026, akaz <--

    super();
}

// НЕПРАВИЛЬНО — маркеры прижаты к нулевой колонке
public void insert()
{
    this.validateSomething();

// + ALK_DEVAX12, DAX_012234, Описание, 08.05.2026, akaz -->
    if (this.AccountNum)
    {
        this.alk_updateRelated();
    }
// - ALK_DEVAX12, DAX_012234, Описание, 08.05.2026, akaz <--

    super();
}
```

Правило одинаково работает на любой глубине вложенности: объявления в
`classDeclaration` — обычно 4 пробела, строки внутри тела метода — 8, внутри
вложенного блока — 12. Ориентир всегда один: **та же колонка, что у первой
строки обрамляемого кода**. То же касается однострочного header-маркера перед
сигнатурой нового метода — он ставится на отступе самой сигнатуры.

### 3. Замена существующего кода (старый сохраняется в `/* ... */`)

```xpp
// + ALK_DEVAX12, DAX_012234, [MON] Доработать отчет по расписанию дежурств, 08.05.2026, akaz -->
/*
//ALK_DEVAX12, DAX_007040, ISH: Прошлая модификация, 15.11.2023, rusl
final class SomeClass extends SomeBase
*/
class SomeClass extends SomeBase
// - ALK_DEVAX12, DAX_012234, [MON] Доработать отчет по расписанию дежурств, 08.05.2026, akaz <--
```

Внутри `/* ... */` — старая строка вместе с её прежним маркером модификации (если был). Новая строка идёт после `*/` и до закрывающего маркера.

### 4. Удаление кода (полностью убрать старое)

```xpp
    // + ALK_DEVAX12, DAX_012234, [MON] Доработать отчет по расписанию дежурств, 08.05.2026, akaz -->
    /*
    old code that we are removing;
    */
    // - ALK_DEVAX12, DAX_012234, [MON] Доработать отчет по расписанию дежурств, 08.05.2026, akaz <--
```

Старый код всегда сохраняется в `/* ... */`, никогда не удаляется без следа.

(В примере §3 выше маркеры стоят на нулевой колонке потому, что обрамляют
объявление класса, которое там и живёт, — правило «по отступу обрамляемого кода»
соблюдено и там.)

## Где проставлять комментарии в `.xpo`

В выгруженных X++ исходниках (`*.xpo`) каждая строка кода метода предварена символом `#`. Комментарий-маркер ставится с таким же `#` и идёт между строк кода метода. Пример:

```
SOURCE #classDeclaration
  #//ALK_DEVAX12, DAX_012234, [MON] Доработать отчет по расписанию дежурств, 08.05.2026, akaz
  #class SomeClass extends Base
  #{
  #    int newField;   // без +/- — объект текущей мод
  #}
ENDSOURCE
```

В **чужом** `classDeclaration` новое поле по-прежнему оборачивают в `+/-`.

## Свойство `Origin` для новых объектов, создаваемых с нуля

Реальный AOS Export всегда проставляет в `PROPERTIES` блоке объекта `Origin #{GUID}` — это
внутренний AX-сгенерированный идентификатор. Когда `.xpo` пишется вручную (`Write`/`Edit`), а
не выгружен из настоящей Axapta (типичный случай для нового проекта, который ещё не разворачивался
в реальном AOS):

- **Не изобретай GUID.** GUID состоит СТРОГО из hex-символов `0-9A-F` — буквы вне этого диапазона
  (например встраивание мнемоники кода модификации: `...-DAX124880001`) делают его невалидным.
  AX откажет при импорте: «Недопустимое значение ... для свойства Origin».
- **Пропускай `Origin` целиком** в `PROPERTIES` нового объекта — оставь только `Name`:
  ```
  PROPERTIES
    Name                #ALK_MyNewClass
  ENDPROPERTIES
  ```
  AX присвоит настоящий Origin сама при первом сохранении/импорте — не нужно ничего подставлять.
- Исключение — GUID `Origin` самого `PRN`-объекта Project при сборке релиза через
  [axapta-project-export](../axapta-project-export/SKILL.md): там GUID генерируется штатно через
  `[guid]::NewGuid()` (валидный случайный hex) и переиспользуется между релизами того же
  проекта — это про сам Project-контейнер, не про тела отдельных объектов.

## Гранулярность маркеров

- Один логический блок изменений = один пара маркеров `// + ... -->` / `// - ... <--`. Не дроби каждую строку отдельно, если они меняются вместе.
- Разные логические блоки в одном методе = отдельные пары маркеров.

### Объект текущей модификации / проекта

Объект «текущей мод»: в файле уже есть маркер **текущей** модификации на уровне объекта — однострочный в `SOURCE #classDeclaration` (класс) или `SOURCE #_changeDeclaration` (таблица, форма) (тот же `DAX_NNNNNN` / проект / ник, что в сессии). Аналогично для других AOT-типов, где есть эквивалентная «шапка» объекта.

| Ситуация | Маркеры |
|----------|---------|
| Новый AOT-объект | **Один** однострочный маркер на объекте (`classDeclaration` у класса, `_changeDeclaration` у таблицы/формы) |
| Новый метод в таком объекте | **Без** header-комментария |
| Правка тела метода такого объекта | **Без** блочных `+/-` |
| Новый метод в **чужом** объекте (стандарт AX, другая мод) | Однострочный header перед сигнатурой |
| Правка **чужого** / старого метода | `+/-` и при замене — старое в `/* */` |

Критерий: маркер текущей мод уже стоит на объекте — этого достаточно для атрибуции всего файла в рамках этой модификации.

### Остальное (чужие объекты)

- Полностью новый метод в чужом объекте = одного однострочного `//<параметры>` перед сигнатурой достаточно. Не оборачивай тело метода маркерами `+/-`.
- Полностью новый класс = однострочный перед `class X extends Y`; **не** дублируй header на каждом методе и **не** ставь `+/-` внутри (см. таблицу выше).

## Проверка перед коммитом

1. Для **чужого** объекта: все ли новые/изменённые строки накрыты маркером?
2. Для объекта **текущей мод**: есть ли один маркер на объекте (`classDeclaration`); нет ли лишних header на методах и `+/-` в телах?
3. Совпадают ли коды проекта/модификации/описание/дата/ник в открывающем и закрывающем маркере `+/-` (если они есть)?
3a. Маркеры стоят на том же отступе, что и обрамляемый код (см. §«Отступ маркеров»), а не прижаты к нулевой колонке?
3b. Для одиночной вставленной/изменённой строки использован хвостовой маркер, а не блок `+/-` (см. §«Одна строка — комментарий в конце строки»)?
4. Старый код, который заменён, сохранён внутри `/* ... */`?
5. Дата актуальна (брать из системы, не выдумывать)?
6. Код модификации в комментариях в canonical-comment форме (`PREFIX_NNNNNN`, ровно 6 цифр)?
7. Достигнут естественный чекпоинт? Если да — спроси про снапшот через [axapta-project-export](../axapta-project-export/SKILL.md).
8. Новые имена локальных переменных/параметров/полей класса (НЕ столбцов таблиц) не совпадают с зарезервированными словами X++ (см. §«Зарезервированные слова X++»)?

## Workflow при первом редактировании в сессии

0. **Preflight ENV-гейт** (см. [setup](../setup/SKILL.md) §«Resolve plugin root» и
   §«Preflight-конвенция») — разреши `$pluginRoot`, затем прогони:
   ```powershell
   python "$pluginRoot\scripts\XPOTools\Modules\config.py"
   ```
   Ненулевой exit code → **остановись**, покажи пользователю ошибки из stderr, направь на
   `/alk-axapta-tools:setup`. Не продолжай работу без полной конфигурации — не спрашивай
   отдельные значения вручную, не подставляй временные дефолты.
1. **Проверь структуру `XPO/`** — обязательны и папка `XPO/` в корне, и AOT-раскладка внутри
   (`XPO/Classes/`, `XPO/Data Dictionary/Tables/`, …), см. [axapta-project-export](../axapta-project-export/SKILL.md) §«Папка XPO/ обязательна». Если структура не такая:
   - `.xpo`-файлы вне `XPO/` (в `src/` и т.п.) или папки `XPO/` нет — **спроси** через `AskUserQuestion`,
     перенести ли их в `XPO/`: перемещение меняет структуру репозитория, не делай его молча;
   - `.xpo` в `XPO/`, но лежат плоско — **спроси**, разложить ли по типам через `organize-xpo`
     (скилл [axapta-project-manage](../axapta-project-manage/SKILL.md));
   - файлов ещё нет (новый проект) — создай пустую `XPO/` перед первым `Write` (ничего не переносится —
     подтверждение не требуется);
   - сообщи о созданной папке / переносе / раскладке одной строкой и продолжай.
2. Прочитай memory: ищи `project_current_modification.md` и `user_alk_profile.md`. Если есть и актуальны — используй их.
3. Если memory нет / устарела / пользователь начал явно новую задачу — спроси через `AskUserQuestion`:
   - Код проекта (по умолчанию из memory, иначе — из `AX_PROJECT_ID`, гарантированно заданной preflight'ом)
   - Код модификации (`DAX_NNNNNN` — принимать в любом виде)
   - Описание (с префиксом типа `[MON]`, `ISH:` и т.п. — спроси, если непонятно)
   - Ник пользователя (по умолчанию из memory, иначе — из `AX_USER_NICK`)
   - Сразу нормализовать полученный код: canonical-settings (`PREFIX-N`) → хранить; canonical-comment (`PREFIX_NNNNNN`) → применять в маркерах.
4. Сохрани новые/обновлённые параметры в memory (типы `project` и `user`). Код модификации хранить в **canonical-settings форме** (дефис, без ведущих нулей).
5. **Прочитай конвенцию именования** (до первого нового идентификатора) — благодаря preflight'у
   на шаге 0 значения уже гарантированно заданы, спрашивать не нужно:
   - Прочитай `AX_OBJECT_PREFIX`/`AX_OBJECT_SUFFIX` (ENV, приоритетно) или `config.local.json`.
   - Запомни на сессию: **новые AOT-объекты** → `UPPER_PREFIX_` (например `ALK_`); **методы/переменные/параметры в существующих** → `lower_prefix_` (например `alk_`).
6. Применяй шаблоны комментариев при каждом `Edit` / `Write`; именуй по двухуровневому правилу из п. 5.

## Конвенция именования новых идентификаторов

Все новые идентификаторы в рамках ALK-модификации именуются с проектным аффиксом. Регистр аффикса зависит от того, **что именно** создаётся:

- **Новый AOT-элемент** (новый объект в дереве AOT — класс, таблица, форма, EDT, перечисление и т.д.): аффикс в **ВЕРХНЕМ** регистре. Пример: `ALK_MyNewClass`, `ALK_MyTable`.
- **Новый метод, переменная или параметр** в существующем стандартном объекте (чьё имя не начинается с `ALK_`): аффикс в **нижнем** регистре. Пример: `alk_buildRelationNotExists`, `alk_notExistsIdSet`, `alk_queryBuildDataSource`.

**Ключевое правило**: если контейнер (класс/таблица/форма) уже является ALK_*-объектом (создан в рамках проекта) — дополнительный аффикс на методы и переменные внутри него **не нужен**.

### Глобальная настройка (ENV или config.local.json)

Источник значений по приоритету: **ENV-переменные** `AX_OBJECT_PREFIX` / `AX_OBJECT_SUFFIX`
(их пишет `/alk-axapta-tools:setup`, переживают обновления плагина) → затем `config.local.json`
(лежит в кэше плагина, стирается при обновлении). Preflight-гейт на шаге 0 workflow уже
гарантирует, что ровно одно из двух полей заполнено — здесь их только читают:

```json
{
  "AX_OBJECT_PREFIX": "alk_",
  "AX_OBJECT_SUFFIX": ""
}
```

| Поле | Значение | Смысл |
|------|----------|-------|
| `AX_OBJECT_PREFIX` | `"alk_"` | Аффикс для методов/переменных/параметров в **существующих** объектах (lowercase + `_`) |
| `AX_OBJECT_SUFFIX` | `""` | Постфикс (альтернатива PREFIX). Пусто = не используется |

Ровно одно из двух полей обязательно заполнено (проверяется preflight'ом, не здесь) —
prefix и suffix никогда не заданы одновременно.

**Деривация аффикса для новых AOT-объектов**: взять `AX_OBJECT_PREFIX` (или, если задан
`AX_OBJECT_SUFFIX` — его) и привести к UPPER. Для префикса дополнительно убедиться, что
оканчивается на `_` (`alk_` → `ALK_`); для постфикса — что начинается с `_`
(`_cdt` → `_CDT`).

Итого из одного поля `"alk_"` получается:
- Члены существующих объектов: `alk_` (as-is)
- Новые AOT-объекты: `ALK_` (UPPER)

### Что именовать с аффиксом

| Что | Регистр аффикса | При prefix `alk_`/`ALK_` | При suffix `_cdt`/`_CDT` |
|-----|-----------------|---------------------------|---------------------------|
| **Новый AOT-элемент** (класс, таблица, форма, EDT, перечисление) | **ВЕРХНИЙ** | `ALK_MyNewClass`, `ALK_MyTable` | `SysMCPSession_CDT` |
| Новый метод в существующем стандартном объекте | **нижний** | `alk_buildRelationNotExists()` | `initMcp_cdt()` |
| Новое поле в `classDeclaration` существующего объекта | **нижний** | `alk_notExistsIdSet` | `mcpSession_cdt` |
| Локальная переменная внутри метода существующего объекта | **нижний** | `alk_joinMode` | `joinMode_cdt` |
| **Параметр нового метода** в существующем объекте | **нижний** | `alk_queryBuildDataSource` | `queryBuildDataSource_cdt` |
| Новый контрол/макрос в существующей форме | **нижний** | `alk_statusBut` | `mcpStatusBut_cdt` |
| Метод/переменная/параметр в своём объекте текущей мод | без аффикса | `buildPopupMenu()`, `_dictRelation` | `buildPopupMenu()` |

**Регистр зависит только от того, ЧТО именуется, а не от вида аффикса.** Правило
одинаково для префикса и постфикса: **имя AOT-объекта — аффикс в ВЕРХНЕМ регистре,
любой член внутри чужого объекта (метод, поле, локальная переменная, параметр,
контрол, макрос) — в нижнем**. Образцы в приложении: объекты `SysMonIncidentTable_CDT`,
члены `axDatabase_cdt`, `canGoMultiThread_cdt`, `copyToUserId_cdt`.

### Предел длины имени — 40 символов

Имя AOT-объекта в AX 2012 ограничено **40 символами** (EDT `SysUtilElementName` —
`STRING(40)`). Если имя не влезает, **сократи его заранее и осмысленно**, а не
оставляй на самотёк: ужимай самые длинные слова, сохраняя смысл, и не трогай
части, несущие техническую нагрузку (обязательные префиксы, аффикс проекта).

```
CIT_DevToolPanel_Display_SysMCPParameters_CDT   45 — не влезает
CIT_DevToolPanel_Display_SysMCPParms_CDT        40 — Parameters -> Parms
```

Здесь сокращено самое длинное слово (`Parameters`), а префикс `CIT_DevToolPanel_`
(его требует механизм кнопок панели) и постфикс `_CDT` остались нетронутыми.

**При любых сомнениях, как сокращать, — спроси пользователя.** Имя объекта живёт
годами и попадает в выгрузки заказчику; неудачное сокращение потом не переименуешь
без миграции. `validate-xpo` проверяет предел автоматически, но подобрать
осмысленный вариант он не может.

### Выравнивание объявлений и присваиваний в столбцы

Объявления переменных и группы присваиваний оформляются **столбцами**: имена
выравниваются по общей колонке, знаки `=` — по своей. Так блок читается как
таблица, а не как рваный текст.

```xpp
// ПРАВИЛЬНО
class SysMonAlertGenerateEngine_CDT
{
    SysMonServiceTableExt_CDT           serviceTable;
    SysMonServiceMetricsExt_CDT         serviceMetrics;
    SysMonServiceMetricsValuesTmp_CDT   serviceMetricsValuesTmp;

    boolean                             traceMode;
    boolean                             skipAlerts;
}

    _alertTableTmp.CheckDateTime    = _checkDateTime;
    _alertTableTmp.AlertSessionId   = _alertSessionId;
    _alertTableTmp.Duration         = _duration;

// НЕПРАВИЛЬНО — колонка «съехала», глазом не сканируется
    SysMonServiceTableExt_CDT serviceTable;
    boolean traceMode;

    _alertTableTmp.CheckDateTime = _checkDateTime;
    _alertTableTmp.AlertSessionId = _alertSessionId;
```

Смысловые группы разделяются пустой строкой — выравнивание считается внутри
группы, а не по всему методу.

**Отдельно проверяй выравнивание после переименований**: когда имя типа или
переменной становится длиннее, колонка ломается именно в тех строках, которых
переименование не коснулось.

### camelCase и общепризнанные аббревиатуры

Имена — в camel-нотации. Исключение — общепризнанные аббревиатуры (`MCP`, `JSON`,
`HTTP`, `EDT`, `SQL`, `XML`): они не «camel-изируются», а сохраняют свой вид, и
регистр зависит от позиции в имени:

| Позиция аббревиатуры | Регистр | Пример |
|---|---|---|
| В начале имени | все буквы **строчные** | `mcpToggle_cdt()`, `httpGet()`, `edtName()` |
| В середине или конце | все буквы **ЗАГЛАВНЫЕ** | `refreshMCPIndicator_cdt()`, `timeoutHandlerMCP_cdt()`, `childNamesJSON()` |

```xpp
// ПРАВИЛЬНО
mcpSession_cdt              // аббревиатура открывает имя -> строчные
initMCP_cdt()               // в середине/конце -> заглавные
refreshMCPIndicator_cdt()
SysMCPJSON_CDT              // имя объекта: обе аббревиатуры заглавными

// НЕПРАВИЛЬНО — аббревиатура «причёсана» под camelCase
MCPSession_cdt              // в начале должно быть строчными
initMcp_cdt()               // в середине должно быть заглавными
refreshMcpIndicator_cdt()
SysMCPJson_CDT
```

Правило действует и для имён AOT-объектов, и для членов; аффикс (`_cdt` / `_CDT`)
живёт по своему правилу регистра из таблицы выше и на аббревиатуры не влияет.

В настройке (`.axapta.json` / ENV) аффикс хранится в **мемберной** форме —
`"AX_OBJECT_SUFFIX": "_cdt"` или `"AX_OBJECT_PREFIX": "alk_"`; форма для имён
объектов выводится из неё приведением к UPPER.

### Зарезервированные слова X++

Список зарезервированных слов X++ (компилятор AX не даст объявить с таким именем
**параметр метода, локальную переменную или поле класса**) — `"$pluginRoot\scripts\XPOTools\Modules\reserved_words.py"`
(`RESERVED_WORDS`, сравнение регистронезависимое; помимо официальных ключевых слов
X++ там же — проектные добавления ALK, например `sessionId`). Источник основной части —
реальный экспортированный список зарезервированных слов Axapta, сверенный с официальной
документацией Microsoft.

**Правило касается параметров методов, локальных переменных и полей класса
(`classDeclaration`).** Поля таблиц (`tableFieldsDeclaration` — столбцы Data Dictionary)
и имена самих таблиц под это ограничение НЕ подпадают — это метаданные AOT, а не
буквальные X++-объявления, и по конвенции ALK они МОГУТ совпадать с зарезервированными
словами; не сверяй и не переименовывай их по этому списку.

**Перед тем как назвать новый параметр, локальную переменную или поле класса** —
сверься со списком (особенно для коротких «бытовых» имён: `date`, `count`, `window`,
`index`, `int`, `str`, `guid`, `select`, `join`, `order`, `print`, `client`, `server`,
`static`, `this`, `new` — их легко выбрать не задумываясь, и они реально
зарезервированы). Если нужное по смыслу имя зарезервировано — используй аффикс
(`alk_date`, `_date`) или синоним (`recDate`, `dateValue`).

**`validate-xpo` проверяет это автоматически** (WARN) для параметров методов, локальных
переменных и полей класса — но только эвристически (regex, не полный парсер X++):
локальные переменные детектируются только в начале тела метода (блок объявлений сразу
после `{`, до первого исполняемого оператора — по конвенции ALK они идут именно так).
Ручная сверка при выборе имени всё равно нужна, авто-проверка — подстраховка, а не замена.

### Применение перед реализацией

**До первого `Edit`/`Write`** с новым идентификатором — аффикс уже гарантированно определён
preflight-гейтом на шаге 0 workflow, здесь только применяют, без переспроса:

1. Определи аффикс по приоритету: **ENV** `AX_OBJECT_PREFIX` / `AX_OBJECT_SUFFIX` → затем `config.local.json` (те же поля).
2. Применяй:
   - новые AOT-объекты → `UPPER(AX_OBJECT_PREFIX или AX_OBJECT_SUFFIX)` → `ALK_`
   - методы/переменные/параметры в существующих → как есть (lowercase) → `alk_`
3. Приоритет при расхождениях: ENV > `config.local.json` > memory (`feedback_alk_naming_convention.md`).

## Anti-patterns — чего НЕ делать

- **Не оборачивай новый метод/класс целиком в блок `// + … -->` / `// - … <--`.**  
  Для полностью нового **чужого** метода достаточно однострочного header перед сигнатурой.  
  Блочные маркеры — только для добавления/изменения строк **внутри существующего чужого** метода. `validate-xpo --strict` поймает ошибку «блок вместо header».
- **Не ставь header на каждый метод** объекта текущей мод и **не ставь `+/-`** при правках внутри него — достаточно маркера в `classDeclaration`.
- Не удаляй старый код «насовсем» — оборачивай в `/* */` внутри маркеров (чужие объекты).
- Не забывай однострочный маркер на **новых методах чужих** объектов (легко пропустить).
- Не используй сегодняшнюю дату «по памяти» — бери из системного контекста.
- Не путай стрелки: открывающий `-->`, закрывающий `<--`.
- **Не прижимай маркеры к нулевой колонке**, если обрамляемый код с отступом
  (см. §«Отступ маркеров»). В форме сравнения AX такой блок выпадает из
  структуры метода и мешает читать диф при импорте.
- Не используй комментарии вида `// TODO`, `// fix later` вместо маркеров — даже временный код в чужом объекте должен быть помечен.
- Не пиши описания на английском, если в memory/проекте принят русский (и наоборот).
- **Не фабрикуй GUID для `Origin`** нового объекта (см. §«Свойство `Origin` для новых объектов»).
  Либо валидный `[guid]::NewGuid()`, либо (для тел объектов, не Project) — вообще не указывай
  `Origin`, оставь только `Name` в `PROPERTIES`.
