# Axapta MCP Helper

Живой MCP-сервер (`axapta-mcp-server`) даёт прямой доступ к запущенной сессии
Dynamics AX 2012 через поллер в X++ — чтение AOT, компиляция, поиск, запись —
без похода к офлайн-выгрузке `.xpo` и без ручного экспорта/импорта на каждый
шаг. Этот навык — эксплуатационное знание о том, КАК пользоваться этим
набором инструментов правильно: когда какой источник данных предпочесть, как
провести `changeset_apply` через весь его жизненный цикл, на какие грабли уже
наступали и как их обходить.

Отдельный скилл `axapta-mod-comments` остаётся обязательным для самой
разметки маркеров модификации — этот навык его не заменяет, а показывает,
где и как её применять в контексте живых MCP-вызовов (см. раздел «Формат для
changeset_apply» в `axapta-mod-comments`).

## 1. Подключение и персональный ключ

Сервер держит два канала: поллер X++ (Windows Negotiate, подключает сама
панель разработчика в AX-клиенте) и MCP-канал (персональный API-ключ,
`Authorization: Bearer <ключ>` в MCP-конфиге клиента).

Ключ получить одним из двух равноценных способов:
- **браузер** — открой `http://<host>:<port>/handshake` (та же корпоративная
  сеть, Negotiate проходит прозрачно), нажми «Показать/выпустить», скопируй
  ключ (показывается один раз);
- **панель AX** — кнопка/меню MCP в `CIT_DevToolPanel`, тот же принцип.

Автоматизированный браузер (Playwright и аналоги) часто падает на Negotiate
(`ERR_INVALID_AUTH_CREDENTIALS`). Для выпуска ключа используй системный
браузер Windows или PowerShell (7+: параметр `-AllowUnencryptedAuthentication`
есть только в pwsh, Windows PowerShell 5.1 упадёт на нём с parameter not found):

```powershell
# Проверка, что handshake доступен под текущим пользователем (pwsh 7+)
Invoke-WebRequest "http://<host>:<port>/handshake" `
  -UseDefaultCredentials -AllowUnencryptedAuthentication -TimeoutSec 20
```

Хранилище ключей (`KeyStore`) привязано к Windows-учётке, а не к среде —
токен один и тот же для всех систем/сред, которые обслуживает данный сервер
(`AX_MCP_KEY`, без суффикса среды). Топология на 13.08.2026 — по процессу на
среду (dev/test/prod, разные порты), единый сервер на все системы компании
запланирован (см. проектную память по многосистемному реестру), поэтому
сейчас при переключении на другой порт/процесс ключ нужно перевыпустить и
обновить значение переменной заново — имя переменной от этого не меняется.

Типичный MCP-endpoint: `http://<host>:<port>/mcp` (streamable HTTP /
`text/event-stream`). Пример ответа `initialize`: `serverInfo.name` =
`axapta-mcp-server`.

### Ключ — в переменную окружения, конфиг — на уровне пользователя

Конфиг MCP-клиента — **на уровне пользователя/компьютера, не проекта**:
проектный `.mcp.json` перекрывает общий и рискует уехать в git вместе с
ключом, если кто-то впишет его буквально вместо плейсхолдера.

Claude Code — одна команда, конфиг уходит в `~/.claude.json`:

```powershell
claude mcp add --scope user --transport http axapta `
  http://<host>:<port>/mcp --header 'Authorization: Bearer ${AX_MCP_KEY}'
```

Cursor не поддерживает CLI для этого и не везде разворачивает `${VAR}` в
`headers` — надёжнее всего вписать то же тело в `~/.cursor/mcp.json` вручную;
если подстановка не сработает (проверяется по `initialize`/401), временно
впиши в это поле открытый ключ вместо плейсхолдера — это единственное
компромиссное место, где ключ хранится буквально, и его нужно обновлять при
каждом перевыпуске:

```json
{
  "mcpServers": {
    "axapta-mcp-server": {
      "url": "http://<host>:<port>/mcp",
      "headers": {
        "Authorization": "Bearer ${AX_MCP_KEY}"
      }
    }
  }
}
```

После записи конфига:
1. **Полный перезапуск** IDE/CLI (Reload Window не хватает — переменная
   окружения читается только при старте процесса).
2. Если IDE спросит — разреши сервер `axapta`/`axapta-mcp-server`.
3. В каталоге инструментов Cursor имя часто выглядит как
   `user-axapta-mcp-server` (префикс `user-` от user-level mcp.json) —
   это тот же сервер.
4. Проверка: вызови `ax_session_status` (без параметров), либо
   `claude mcp get axapta` (Connected/Failed to connect).

Если сервер отвечает на `initialize` при ручной проверке curl/Invoke-WebRequest,
а в агенте tools нет — почти всегда конфиг не user-scope (например, случайно
остался проектный `.mcp.json`, перекрывающий общий) или сессия IDE стартовала
до того, как `AX_MCP_KEY` появилась в окружении — не «мёртвый» MCP.

## 2. Карта инструментов и источников данных

Три класса инструментов по требованиям к живому поллеру:

| Класс | Инструменты | Требует живой поллер? |
|-------|-------------|------------------------|
| Работают всегда | `ax_source_find` (зеркало+ripgrep), `ax_xref_find` (SQL) | Нет, если включены Mirror/Sql на сервере |
| Предпочитают live, падают в зеркало | `aot_get_source`, `aot_exists` | Нет при включённом Mirror — иначе да |
| Только live | `ax_compile*`, `ax_run_job`, `ax_test_run`, `changeset_apply`, `aot_get_property`, `ax_import_xpo`, `ax_project_status`, `ax_project_set_default`, `ax_project_add_objects`, `ax_project_create`, остальные | Да, без исключений |

Без живого поллера и без Mirror/Sql инструменты «только live» отвечают
СРАЗУ понятной ошибкой («требует живого поллера…»), не таймаутом на
120 секунд — если видишь такую ошибку, дело не в сети, а в том, что AX-
клиент сейчас не подключён (или у тебя вообще нет AX-клиента — см. раздел 8).

**Метка `origin` в ответах `aot_get_source`/`aot_exists`/`ax_source_find`**
говорит, откуда пришли данные — читай её, прежде чем доверять содержимому:

| origin | Значит | Как действовать |
|--------|--------|------------------|
| (нет поля, голый текст) | Живой AOT, только что прочитан | Доверяй как актуальному |
| `mirror-confirmed` | Зеркало + SQL подтвердила: не менялось с экспорта | Можно доверять как живому |
| `mirror` + `changedSinceExport: true` | SQL подтвердила: МЕНЯЛОСЬ с экспорта | Код отстал — перечитай через живой поллер, если он есть |
| `mirror` + `stale: true` | SQL недоступна, свежесть неизвестна | Смотри `exportedAt` — если давно, перечитай live |

**Зеркальный ответ НИКОГДА не годится как база для `expectedHash`** в
`changeset_apply` — запись всегда требует свежего `aot_get_source` без
`methodName`, прочитанного через ЖИВОЙ поллер, непосредственно перед сборкой
changeset'а.

## 3. Жизненный цикл `changeset_apply`

```
aot_get_source (без methodName) → hash считает сам инструмент (кэш) →
маркер модификации в Source (см. axapta-mod-comments) →
changeset_apply → guard на сервере (expectedHash, маркер, чёрный список) →
ack: operationId, status=in_progress, confirmation="auto"|"manual" →
очередь X++ → живая перепроверка hash в AOT → форма предпросмотра
(только если confirmation="manual") → опрашивай ax_operation_status,
пока не придёт финальный статус
```

Финальный статус — не мгновенный: между `changeset_apply` (guard) и записью
проходит как минимум один тик поллера, а если открылась форма предпросмотра —
столько, сколько человек решает. Не блокируй разговор ожиданием одного
вызова — опрашивай `ax_operation_status` по `operationId` отдельными шагами.

**Поле `confirmation` в ack — читай его сразу, до первого опроса статуса.**
Оно говорит, откроется ли форма превью, ещё ДО того, как это произойдёт:

- **`confirmation: "manual"`** — весь changeset или его часть вне персональной
  маски пользователя `NoConfirmMask`: форма превью откроется и может ждать
  сколько угодно (обед, ночь). Здесь уместно сказать пользователю «жду
  подтверждения в AX».
- **`confirmation: "auto"`** — весь changeset попадает под `NoConfirmMask` (и
  не содержит `delete` — удаление всегда уходит в форму, даже под маской).
  Форма НЕ откроется вообще. **Не говори пользователю «жду подтверждения» —
  подтверждать нечего.** Сразу опрашивай `ax_operation_status`: финальный
  статус обычно приходит за один тик поллера (~5-10 секунд), а не за то время,
  что человек решает. Тот же признак дублируется в финальном
  `resultPayloadJson` (`confirmation`) — там это уже факт, а не прогноз.

### Реакция на каждую ветку

- **Guard отказал hash-конфликтом** («expectedHash не совпадает») — перечитай
  объект через `aot_get_source` заново (БЕЗ methodName), пересобери changeset
  с новым hash. НЕ повторяй вызов со старым hash — он снова откажет.
  Известная деталь: если хеш не сошёлся с первой попытки, попробуй
  пересчитать с ОДНИМ добавленным `\n` в конец текста — частая причина
  расхождения в этом типе серверов (склейка методов через `\n\n`).
- **Форма предпросмотра отклонена человеком** (`status: rejected`) — прочитай
  `resultMessage`/комментарий разработчика. Это осознанное решение, не сбой:
  не повторяй тот же вызов, учти комментарий или уточни задачу у пользователя.
- **Ошибки компиляции после записи** — правь код и пересобирай `Source` от
  `newHash` из результата (`objectsFragment`), НЕ от старого `expectedHash` —
  объект уже записан, повторный `aot_get_source` не обязателен, если
  `newHash` уже есть в ответе.
- **`blocked`/guard отказал вообще** — НЕ повторяй вызов вслепую: причина в
  тексте ошибки (протухший AX-слой, объект в чёрном списке без
  `allowProtected`, отсутствие маркера модификации) — исправь то, что
  реально названо.

## 3a. Импорт xpo через MCP (`ax_import_xpo`)

Открывает штатный диалог импорта в AX-клиенте (как Ctrl+Shift+I), подставляет
файл, раскрывает «Отобразить подробности» и ждёт решения РАЗРАБОТЧИКА —
инструмент никогда не жмёт «Импорт» сам. Возвращает `operationId` сразу,
итог — через `ax_operation_status`, когда человек закроет диалог (импорт или
отмена).

Ровно один источник файла:
- `path` — абсолютный путь **на машине AX-клиента** (не на твоей!) —
  используй, если файл уже там (например `XPO/_release/SharedProject_*.xpo`);
- `content` — текст xpo целиком (с BOM/CRLF, как отдаёт `aot_export_xpo` с
  `includeContent=true` — сервер сам восстановит BOM/CRLF, даже если пришло с
  `bomStripped:true`) — используй, если файла на машине клиента нет. Сервер
  кладёт содержимое во временную папку клиента и удаляет её сразу после
  закрытия диалога — файл живёт там ровно на время решения разработчика.

По умолчанию (`addToProject: true`) успешно импортированные объекты сами
добавляются в проект AOT по умолчанию — см. раздел 3c.

## 3b. Работа с AOT-проектами (`ax_project_*`)

- `ax_project_status` — прочитать, какой проект сейчас по умолчанию
  (`xUserInfo.startupProject`), существует ли он и сколько в нём объектов
  (грубая оценка). Дёшево, вызывай перед `changeset_apply`/`ax_import_xpo`,
  если непонятно, куда попадут объекты.
- `ax_project_set_default` — переключить проект по умолчанию на уже
  существующий (по `projectCode`+`projectJob` записи реестра ИЛИ по имени
  AOT-проекта).
- `ax_project_add_objects` — добавить явный список объектов в текущий проект
  по умолчанию, без диалога.
- `ax_project_create` — создать НОВЫЙ проект под запись реестра, у которой
  ещё нет `ProjectNodeName` (проверь `ax_project_job_find` сначала).
  Интерактивный (диалог подтверждения, тот же принцип, что у
  `ax_project_job_create`). Создаёт **пустой** проект — без стандартного
  набора групп (Tables/Classes/Forms/Security...): реальные группы
  появляются сами по мере добавления объектов.

«Запись реестра» здесь — реестр разработок ALK: запись идентифицируется
парой `projectCode`+`projectJob`, а привязка к AOT хранится в её поле
`ProjectNodeName`. Инструменты реестра `ax_project_job_find` (найти запись
и её привязку) и `ax_project_job_create` (завести новую запись,
интерактивный) в этом скилле подробно не описаны — актуальные параметры
смотри в описаниях самих инструментов в каталоге MCP-сервера.

## 3c. Автодобавление в проект по умолчанию

И `changeset_apply`, и `ax_import_xpo` по умолчанию (`addToProject: true`)
сами добавляют успешно применённые/импортированные объекты в текущий проект
по умолчанию — итог в поле ответа `project: {name, added, reason?}`.
`reason` появляется, если добавить не удалось (чаще всего — проект по
умолчанию не назначен: `startupProject` пуст). Если объекты должны попасть в
конкретный релизный проект (`axapta-project-export`), убедись ПЕРЕД сессией
правок, что нужный проект — дефолтный (`ax_project_status`/
`ax_project_set_default`), иначе они будут падать не туда.

## 4. Известные ловушки живого AOT

- **Самомодификация — объект не может надёжно записать сам себя, пока сам
  же исполняет эту запись.** Никогда не применяй `changeset_apply` к объекту,
  метод которого прямо сейчас находится в стеке вызовов, обслуживающих этот
  же вызов (типично — сами классы сервера-поллера в его собственной X++
  части, если они есть в проекте; или Form, чей текущий экземпляр обрабатывает
  запрос на добавление в себя же новых контролов/методов). Наблюдавшиеся
  проявления: `AOTadd` падает с «Невозможно создать узел» (для активно
  исполняющейся Form), либо запись в AOT проходит, но живой экземпляр в
  памяти теряет часть полей до перезапуска процесса. Обход — подготовить
  итоговый `.xpo`-фрагмент и попросить разработчика импортировать вручную
  через MorphX, либо просто не трогать changeset_apply'ем то, что прямо
  сейчас его обслуживает.
- **`changeset_apply` ЗАПИСЫВАЕТ в AOT даже если следующая за записью
  компиляция упала.** Проверка результата — это `compile.errorCount` в
  ответе, не сам факт «changeset_apply вернул успех». Особенно важно для
  методов-таймеров (`tick()` и подобных, вызываемых из `Info.addTimeOut`) —
  синтаксическая ошибка там останавливает сам механизм, которым можно было
  бы прислать исправление, и требует ручного вмешательства в MorphX.
- **У `Form` нет whole-object `aot_get_source`** (падает «исходник пуст» без
  `methodName`) — значит нет и `expectedHash` для формы целиком; изменения
  форм идут методами по отдельности, либо свойствами дизайна
  (`changeKind: "property"`), либо ручным `.xpo`-импортом для новых
  контролов, которые `changeset_apply` создавать не умеет вообще.
- **`changeKind: "create"` пишет ТОЛЬКО `classDeclaration`.** Если положить в
  `Source` весь класс (объявление + тела методов) одним куском, всё целиком
  уедет в `classDeclaration`, а не разложится по методам — инструмент это
  отбивает гардом до записи («Source должен содержать ТОЛЬКО объявление
  класса»). Правильный способ с самого начала — ОДИН вызов `changeset_apply`
  с НЕСКОЛЬКИМИ элементами `changes[]`: первый `changeKind: "create"` (только
  `class X extends Y { поля }`, без тел методов, `methodName` пустой),
  остальные `changeKind: "method"` (по одному на метод, `methodName`
  заполнен) — узел метода `changeset_apply` создаёт сам, объект из `create`
  уже существует к моменту их применения.
- **Правки свойств (`changeKind: "property"`) не оставляют маркера
  модификации в самом AOT** — у узла свойства нет текстового `Source`, куда
  можно вписать комментарий. Единственный след — запись в audit-логе
  сервера. Если это важно для проекта — задокументируй правку отдельно
  (например в описании задачи), не полагайся на то, что маркер найдётся
  в самом объекте.

## 5. Выбор источника и режим записи

Основной путь ЗАПИСИ на закрытых корп-стендах — **ручной импорт `.xpo`
разработчиком через MorphX**, а не `changeset_apply`: AI готовит файл,
человек импортирует и компилирует сам. `changeset_apply` остаётся рабочим и
полезным для быстрых точечных правок при живом поллере, но не считай его
единственным путём — если задача про массовую правку, новый объект сложного
типа (Table/Query с полной структурой) или про среду без открытого AX-
клиента у тебя под рукой, офлайн-`.xpo` (см. скилл `axapta-project-export`)
часто практичнее.

## 6. Чтение — live vs зеркало vs офлайн xpo

- Есть живой поллер и объект недавно менялся (эта же сессия) → живое чтение,
  доверяй без дополнительной проверки.
- Поллера нет, но подключено Mirror/Sql → зеркало, смотри `origin` (раздел 2).
- Нет ни поллера, ни зеркала → традиционный офлайн-путь: локальная копия
  `.xpo` в репозитории задачи, `ax_source_find`/поиск текстом по файлам.

## 7. Multi-user — что означает статус

`ax_session_status` без параметров отвечает про ТВОЙ поллер (свой ключ = своя
очередь команд, изолированная от остальных разработчиков) — не про сервер в
целом. `versionMismatch: true` значит, что панель AX работает на старом коде
после импорта правок в саму панель/класс-поллер — закрой и открой панель
заново, простой перезапуск сервера тут не поможет. `connectedPollers` в том
же ответе — диагностика, кто ещё сейчас подключён, не детали чужих команд.

## 8. Работа без AX-клиента (консультантский режим)

Если сервер настроен с включёнными Mirror и Sql, доступны без AX-клиента:
`aot_get_source`/`aot_exists` (метка `mirror`/`mirror-confirmed`),
`ax_source_find` (полнотекстовый поиск по локальной выгрузке),
`ax_xref_find` (перекрёстные ссылки по SQL — **индекс строится еженедельным
пакетным заданием на стороне AX, по свежим правкам последних дней он
ОТСТАЁТ** — для недавнего кода надёжнее `ax_source_find`). Инструменты,
которым нужна реальная запись/компиляция (`changeset_apply`, `ax_compile*`,
`ax_run_job`) в этом режиме недоступны в принципе — не пытайся их обойти,
сообщи пользователю, что нужен AX-клиент или живой поллер у кого-то из
команды.

## 9. Диагностика

| Симптом | Действие |
|---------|----------|
| 401 на вызове MCP-инструмента | Ключ невалиден/отозван — перевыпусти через `/handshake` |
| Таймаут ~120с на «только live» инструменте | Поллер офлайн — проверь `ax_session_status`, попроси переоткрыть панель |
| Мгновенная ошибка «требует живого поллера» | Это quick-fail, не сбой сети — тот же смысл, что таймаут, но без ожидания |
| `changeset_apply` вернул `blocked` | Читай `resultMessage` буквально, там названа причина |
| `origin: mirror` с `stale: true` | SQL-проверка свежести недоступна — доверяй `exportedAt`, не самому факту наличия файла |
| `versionMismatch: true` | Панель AX работает на старом коде — переоткрыть панель, не сервер |
| Пустой `ax_xref_find` на заведомо используемом имени | Скорее всего индекс отстал (недельный batch), не «не используется» — проверь `ax_source_find` |
| После Reload нет tools `aot_*`/`ax_*` в агенте | Cursor: проверь `.cursor/mcp.json` или `~/.cursor/mcp.json` (не корневой `.mcp.json`); Claude: `.mcp.json`. Reload + approve сервера |
| Handshake/Playwright: `ERR_INVALID_AUTH_CREDENTIALS` | Negotiate не проходит в headless — системный браузер или PowerShell с `-UseDefaultCredentials -AllowUnencryptedAuthentication` |
| `initialize` по `/mcp` = 200, а IDE без tools | Ключ и сеть ок; конфиг лежит не в том файле для текущего runtime |
