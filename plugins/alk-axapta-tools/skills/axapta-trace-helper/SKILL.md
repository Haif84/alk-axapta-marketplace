# Трассировка и профилирование клиента AX 2012

Клиент AX 2012 не даёт штатных средств понять, **чем он занят**. Диспетчер задач покажет
загрузку процессора, дампы — что поток стоит в ожидании, трассировка RPC — что вызов не
вернулся. Ни один из них не назовёт метод X++ и его вызывающего.

Родная трассировка AX называет. В её событиях есть класс, метод, форма-источник и уровень
вложенности, по которому восстанавливается полный стек вызовов. На живом стенде она за один
пятиминутный замер нашла форму, создававшую 40 695 нативных объектов `DLL` (136 в секунду),
и метод, пересчитывавший карту `UtilElements` для каждого узла дерева — 26 220 обращений
к серверу за 85 секунд.

## Когда применять навык

### Проактивно

- Пользователь жалуется на скорость AX: «тормозит», «подвисает», «долго думает», «не отвечает».
- Заметен непрерывный расход процессора клиентом при отсутствии работы пользователя.
- Перед оптимизацией любого кода, который крутится по таймеру или в цикле, — чтобы мерить,
  а не гадать.
- После правки горячего места — контрольный замер, подтверждающий эффект в цифрах.

### По явному запросу

- «включи трассировку», «сними трассировку», «профилируй клиент», «разбери трассировку».
- «что делает клиент прямо сейчас», «кто вызывает такой-то метод».

### НЕ применять

- Для правки кода X++ — маркеры модификаций ставит `axapta-mod-comments`.
- Для сборки выгрузок и раскладки XPO — `axapta-project-export` и `axapta-project-manage`.
- Для разовой проверки «жив ли AOS» — там хватит журнала событий, трассировка избыточна.

## Resolve plugin root

Перед вызовом скриптов разреши `$pluginRoot` по канонической процедуре из
[setup](../setup/SKILL.md) §«Resolve plugin root (Claude + Cursor)», заменив в проверках
`scripts\XPOTools` на `scripts\AxTrace`.

## Исполнители

| Задача | Команда |
|---|---|
| создать набор сборщиков | `ax-trace setup -Path <куда писать> [-MaxMB 512]` |
| начать / остановить запись | `ax-trace start` / `ax-trace stop` |
| состояние набора | `ax-trace status` |
| забрать файл из папки СИСТЕМЫ | `ax-trace fetch -Dest <папка>` |
| общая сводка | `analyze-trace summary <файл>` |
| горячие методы | `analyze-trace hot <файл> [--limit N]` |
| кто вызывает метод | `analyze-trace stack "<метод>" <файл>` |
| дерево вызовов за окно | `analyze-trace tree <файл> --since HH:MM:SS --until HH:MM:SS` |
| серверные вызовы | `analyze-trace rpc <файл>` |
| зависшие вызовы | `analyze-trace hung <файл>` |

Fallback при не настроенном PATH:

```powershell
& "$pluginRoot\scripts\AxTrace\ax-trace.ps1" setup -Path C:\ProgramData\AxTrace
python "$pluginRoot\scripts\AxTrace\analyze-trace.py" hot C:\traces\axtrace-20260807-1046.etl
```

## Алгоритм

### 1. Спроси, куда писать трассировку

Каталог должен быть **доступен учётной записи СИСТЕМА** — набор работает от её имени.
Профиль пользователя не годится. По умолчанию предлагай `C:\ProgramData\AxTrace`.
Спрашивай вопросом, не решай молча: на рабочих машинах системный диск бывает почти полон,
а трассировка на горячем клиенте пишет **до гигабайта в минуту**.

### 2. Создай набор (один раз на машине)

```powershell
ax-trace setup -Path <каталог> -MaxMB 512
```

Скрипт сам запросит повышение прав. Буфер создаётся **кольцевым**: при достижении предела
старые события вытесняются новыми, запись не обрывается.

### 3. Снимай прицельно

```powershell
ax-trace start
# воспроизведи проблему: открой форму, дождись подвисания, поработай 2-5 минут
ax-trace stop
ax-trace fetch -Dest .\traces
```

Не оставляй запись надолго. Пять минут на нагруженном клиенте дают 150–700 МБ, а разбор
раздувает файл ещё вшестеро.

### 4. Начни разбор со сводки

```powershell
analyze-trace summary .\traces\axtrace-20260807-1046.etl
```

Она покажет окно времени, число событий и топы. Конвертация `.etl` в XML делается
автоматически и занимает минуты на крупных файлах.

### 5. Найди горячее место

```powershell
analyze-trace hot .\traces\axtrace-20260807-1046.etl --limit 30
```

**Как читать.** Одинаковое число вызовов у нескольких методов почти всегда означает,
что они в одном цикле. Ищи не самый частый метод, а самый частый **корень**.

Пример из живого разбора:

```
  157 267  Map.exists
  157 267  DateTimeUtil.applyTimeZoneOffset
  149 970  Map.lookup
```

Совпадение 157 267 у первых двух — признак одного цикла. Настоящим виновником оказался
`SysAOTExport.calcUtilMap` из нижней части списка: он вызывался повторно и на каждом вызове
заново перебирал всю таблицу.

### 6. Выясни, кто это вызывает

```powershell
analyze-trace stack "DLL.new" .\traces\axtrace-20260807-1046.etl
```

Отчёт даёт цепочки предков с долями. Реальный пример — 92% всех созданий нативных обёрток
пришли из одного места:

```
   20 335  (50.0%)
           SysSetupFormRun.timeoutHandler <CIT_DevToolPanel>
             └─ SysSetupFormRun.step
               └─ SysSetupFormRun.processWindowsChanges
                 └─ SysSetupFormRun.getWindows
                   └─ WinAPI.FindWindowEx
```

### 7. Проверь обмен с сервером

```powershell
analyze-trace rpc .\traces\axtrace-20260807-1046.etl
```

Смотри на пару «число вызовов + переданные байты». Десятки тысяч `ServerNext` означают
построчный перебор таблицы вместо выборки одним запросом.

### 8. Померь после правки

Повтори замер в тех же условиях и сравни числа. Именно так подтверждается эффект:
`DLL.new` упал с 40 695 до 3 303, а объём записи — с 66 до 30 МБ/мин.

## Как читать отчёты: проверенные ловушки

**`AxRC` у `ServerBuildList` — не код ошибки, а число элементов в списке.**
Значения 13100, 20095, 25125 пугают, но это размеры выборок.

**Одинаковое время ещё не значит «вызвал».** Связь устанавливается только по `AxNestLevel`,
а не по близости меток времени. Дважды на этом ошибались: чтения AOT приписали поллеру
только потому, что он отработал за сто миллисекунд до них. На деле поллер к тому моменту
уже закончил, а чтения сделал другой код.

**Отсутствие событий X++ рядом с серверным вызовом означает, что вызов сделал нативный слой
MorphX**, а не код X++. Так выглядят раскрытие узла в дереве AOT, открытие редактора,
компиляция. Искать в этом случае X++-виновника бесполезно.

**Много вызовов не равно «плохо».** Пример: `SysMCPJSON_CDT.hexDigit` дал 23 256 вызовов
и возглавил список. Разбор показал, что это разовая цена разбора двух пакетов JSON:
кириллица кодируется как `\uXXXX`, каждый символ требует четырёх обращений. Дефекта нет.
Сначала смотри, сколько раз отработала **вся цепочка**, и лишь потом делай выводы.

**Нециклический набор обрывается сам.** Если набор создан не этим скиллом, проверь режим:
с фиксированным пределом 2048 МБ на горячем клиенте запись прекращается через две минуты,
причём молча.

## Anti-patterns

- **Оставлять трассировку включённой надолго.** До гигабайта в минуту; системный диск
  заполняется за часы. Включил, воспроизвёл, выключил.
- **Читать `.etl` прямо из каталога набора.** Он создан СИСТЕМОЙ, обычная учётная запись
  его не откроет. Всегда через `ax-trace fetch`.
- **Запускать `logman` без повышения.** Ответит `Access Denied`, причём набор при этом
  вообще не виден в списке — легко решить, что его нет.
- **Делать выводы по одному замеру.** Нагрузка неровная, всплесками. Сравнивай два замера
  в одинаковых условиях.
- **Оптимизировать самый частый метод из `hot`.** Почти всегда он лишь внутренний цикл.
  Правится корень цепочки из `stack`.

## Диагностика падений (редко)

Применяется, когда клиент не тормозит, а обрывается с диалогом «Сервер завершил сеанс».

**Найди зависший вызов:**

```powershell
analyze-trace hung .\traces\axtrace-20260807-1046.etl
```

Отчёт покажет серверные вызовы, у которых есть начало и нет завершения. Дальше — окно
вокруг него через `analyze-trace tree --since --until`, чтобы увидеть, какой метод X++
его выпустил.

**Отличай замирание от отказа.** Это разные события, разнесённые во времени: клиент сначала
надолго встаёт, и лишь потом вызов срывается. Трассировка, остановленная по признаку
«процесс не отвечает», самого отказа не содержит — его надо ловить по событию журнала.

**Признак настоящего клина** — процесс не отвечает N проверок подряд **и** при этом не
тратит процессорное время. Одного `Responding=False` мало: так же выглядит занятый работой
интерфейс.

**Журналы событий.** Провайдер `Dynamics Server 01` — серверная сторона (события 151
рассинхрон версий, 117 нехватка памяти SQL, 180 ошибки RPC). Провайдер
`Microsoft Dynamics AX` — клиентская, и он **не зарегистрирован** в реестре журнала:
`.Message` пустой, данные брать через `([xml]$_.ToXml()).Event.EventData.Data`.
Event Viewer для него подставляет расшифровку системного кода — надпись «Система обнаружила
неверный номер сегмента» у события 180 это артефакт отображения, а не ошибка.

**Дампы, если трассировки не хватило.** `Ax32.exe` — **32-разрядный** (`Machine = 0x014C`),
а `Ax32Serv.exe` 64-разрядный. Снимать клиент 64-битным ProcDump бесполезно: в дампе
окажется только прослойка WOW64, стеки будут состоять из `wow64cpu!TurboDispatchJumpAddressEnd`.
Нужен 32-битный `procdump.exe`, разбирать — `Debuggers\x86\cdb.exe`.
Отсутствие дампа WER — тоже улика: значит процесс завершился штатно, а не упал.
