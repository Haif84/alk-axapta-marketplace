# Как устроено сжатие контекста в Claude Code

Разведка 2026-09-16 по установленному `claude.exe` 2.1.269, а не по
документации: часть фактов ниже в документации отсутствует или сказана иначе.
Путь бинаря:
`~/AppData/Roaming/npm/node_modules/@anthropic-ai/claude-code/bin/claude.exe`.

## Механика

Сжатие — отдельный запрос к основной модели сессии с той же историей,
системным промптом и инструментами. Своей модели у сжатия нет, настройки
выбрать другую тоже нет: сводку пишет та модель, что стоит в сессии.

Промпт сжатия зашит в бинарь и состоит из трёх частей:

1. Преамбула «CRITICAL: Respond with TEXT ONLY», запрет вызывать инструменты.
2. Шаблон разбора: хронологически по каждому сообщению, вывод обязан быть
   блоком `<analysis>`, затем блоком `<summary>`.
3. Необязательный хвост `Additional Instructions:` с произвольным текстом.

После сжатия история сообщений заменяется сводкой, id сессии и файл `.jsonl`
те же, SessionStart с матчером `compact` срабатывает.

## Точки управления

Третья часть промпта — единственный рычаг, но он шире, чем «аргумент команды».
В `Additional Instructions:` попадают, склеенные вместе:

- текст, набранный владельцем после `/compact`;
- **stdout хуков PreCompact** — в коде это `newCustomInstructions`.

Значит постоянные правила сжатия задаются хуком, без ручного набора строки
фокуса, и одинаково работают на ручном и на автоматическом сжатии.

Вход PreCompact, сверх общих полей сессии:

```json
{ "hook_event_name": "PreCompact",
  "trigger": "manual" | "auto",
  "custom_instructions": "строка после /compact или null" }
```

Хук различает ручное сжатие и автоматическое и видит, что уже набрал владелец.

Заблокировавший хук даёт `blockedBy`: сжатие пропускается, в интерфейсе
`compact blocked by PreCompact hook`. То есть условия сжатия тоже управляемы.

PostCompact получает готовую сводку в поле `compact_summary` — её можно
проверить или сложить в файл.

Внутри сабагентов правила другие: при агентском контексте PreCompact отдаёт
только `blockedBy`, инструкции не добавляются, а PostCompact не запускается
вовсе. Это чтение кода, замером не подтверждено.

## Пороги и выключение

| Рычаг | Что делает |
|---|---|
| `autoCompactEnabled` | включает и выключает автосжатие |
| `autoCompactWindow` | порог автосжатия в settings.json |
| `CLAUDE_CODE_AUTO_COMPACT_WINDOW` | тот же порог переменной окружения |
| `--autocompact`, `/autocompact` | разовый и сохраняемый порог |
| `DISABLE_COMPACT=1` | только ручное сжатие, иначе упор в лимит |

Ключа `compactInstructions` в настройках нет — проверено, в бинаре строки нет.

## Цена

В коде есть предрасчитанная сводка и причины отказа от неё:
`miss_custom_instructions` и `miss_hook`. Читается это так: наличие
инструкций или хука сжатия отменяет заготовку, и сводка считается живым
ходом. Вывод из минифицированного кода, замером не подтверждён — от него
зависит, дешевле ли хук ручной строки фокуса (`tech-debt.md` п. 21).

## Чего нельзя

- Заменить базовый промпт сжатия: добавляется только хвост.
- Назначить сжатию свою модель, в том числе дешёвую.
- Подставить свою функцию сводки в Agent SDK: там те же два хука, вызова
  вроде `compact()` нет.

## Как перепроверить на новой версии

Строки и схемы лежат в бинаре открытым текстом:

```bash
EXE=~/AppData/Roaming/npm/node_modules/@anthropic-ai/claude-code/bin/claude.exe
grep -a -c -o 'PreCompact' "$EXE"
perl -0777 -ne 'while(/hook_event_name:"PreCompact"/g){ print substr($_, pos($_)-20, 900) }' "$EXE"
perl -0777 -ne 'while(/function Wze\(/g){ print substr($_, pos($_)-20, 700) }' "$EXE"
```

Имена функций минифицированы и от версии к версии меняются; искать по
устойчивым строкам `Additional Instructions:`, `newCustomInstructions`,
`blockedBy`, `miss_hook`.

|---|---|
| Системный промпт | 4.2k |
| Инструменты | 11.5k |
| Память | 4.6k |
| Навыки | 1.4k |
| Свои агенты | 0.1k |
| **База, итого** | **21.7k** |
| Сообщения | 25.5k |
| Буфер автосжатия | 33.0k |

Отсюда два факта.

Пол после сжатия — база плюс сводка, ≈21.7k + 2–4k ≈ 25k, а не 40k, как
предполагает `tech-debt.md` п. 19. Сжатие со 120k даёт ~25k, то есть срезает
почти все сообщения; экономия против новой сессии в том, что база не
перечитывается заново холодной.

Буфер автосжатия 33k при окне 1M означает срабатывание около 967k — на
бюджете 100–150k автосжатие не наступает никогда. Штатное сжатие у нас
только ручное; порог опускается `autoCompactWindow`, если понадобится
автоматика.

## Семейство механизмов, а не одно сжатие

Разбор 2026-09-16 по списку событий телеметрии в бинаре 2.1.269 и по
документации. Событий сжатия десять: `compact_manual`, `compact_auto`,
`compact_reactive`, `compact_partial`, `compact_snip`, `compact_precomputed`,
`compact_micro_keep_recent`, `compact_hint_reject`,
`compact_context_cap_enforcement`, `compact_fab_check`. Рядом отдельное
семейство `context_collapse_*` (`apply`, `restore`, `recover_413`,
`ctx_agent_spawn`) со своим состоянием в сессии — `contextCollapseCommits`,
`contextCollapseSnapshot`, то есть схлопывание обратимо. Реализация
`context_collapse` по минифицированным именам не читается; замером не
проверено.

### Микросжатие: чистка старых tool_result

Отдельный от сводки механизм. Из кода:

| Параметр | Значение |
|---|---|
| Хранить последних результатов | 5 |
| Минимум экономии, иначе не трогает | 20 000 токенов |
| Чем заменяется | путь к файлу `<persisted-output>` либо `[Old tool result content cleared]` |
| Триггер | отказ сервера с подсказкой о контексте (422/424), падение стрима в нефлоу |

Содержимое не теряется: оно уходит в файл, а в контексте остаётся строка
`Tool result saved to: <путь>` и предложение прочитать файл — тот же приём,
что у нашего правила «вывод больше 12k в файл».

Есть флаг `tengu_hazel_osprey` с полом 75 000 токенов; по умолчанию выключен.
Если его включат удалённо, чистка начнёт срабатывать прямо в нашей рабочей
зоне 100–150k, и старые результаты инструментов будут уезжать в файлы без
нашего участия.

### Серверный аналог в API

`clear_tool_uses_20250919` (бета `context-management-2025-06-27`): порог
100k входных токенов, `keep` 3 вызова, `clear_at_least`, `exclude_tools`,
`clear_tool_inputs`. Работает на стороне сервера до того, как модель увидит
промпт; клиент хранит полную историю. Документация прямо говорит: чистка
обнуляет кэш промпта и вызывает запись кэша заново — ради этого и существует
`clear_at_least`. Тот же счёт применим к нашему `/compact`: после сжатия
префикс новый, значит один платный прогрев кэша (в `/usage` он помечается
как `expected rebuild`).

### Предрасчитанная сводка: что её отменяет

Функция выбора (минифицированная `b`) читается однозначно:

1. заданы инструкции владельца — `miss_custom_instructions`, заготовка не берётся;
2. сработал PreCompact-хук — `miss_hook`, заготовка не берётся;
3. иначе берётся заготовка, в телеметрию идёт `precomputeReuse`.

Отсюда вывод для `tech-debt.md` п. 21, обратный ожидаемому: постоянный
PreCompact-хук делает платным **каждое** сжатие, включая автоматические,
потому что отменяет заготовку всегда. Ручная строка отменяет её только там,
где владелец её набрал.

### Третий путь: правило в CLAUDE.md

Прежний вывод («секции фокуса в CLAUDE.md нет», решение
`2026-09-15-compact-at-threshold.md`) верен буквально и неверен по сути.
Разбора секции в бинаре действительно нет, но сжатие идёт с тем же системным
промптом, куда CLAUDE.md уже вшит, — и заготовку считает тот же путь запроса.
Значит правило вида «при сжатии сохраняй список изменённых файлов и команды
тестов», записанное в CLAUDE.md, влияет на сводку и **не** отменяет заготовку,
в отличие от хука и ручной строки. Документация Anthropic советует ровно это.
Вывод из чтения кода, замером не подтверждён.

### Частичное сжатие

`Esc+Esc` / `/rewind` даёт «Summarize from here» и «Summarize up to here» —
в бинаре это варианты `from` и `up_to` того же промпта (событие
`compact_partial`). Второй сжимает раннюю часть, оставляя свежую целиком:
для нашего шва это точнее, чем сжатие всего.

### Практики с сайта, которые нас касаются

- `/clear` не стоит ничего, `/compact` — большой запрос по всей истории.
- `/btw` отвечает на побочный вопрос, не кладя ответ в историю.
- При возобновлении большой сессии после перерыва Claude Code на Pro/Max
  предлагает продолжить со сводки — прямой конкурент нашему handoff.
- В `/usage` есть строка кэша: доля входа из кэша, промахи и отдельно
  «ожидаемые перестройки» после сжатия или чистки результатов.
- Фоновые расходы простоя — до $0.04 за сессию.

## Что показал живой замер 2026-09-16

Сессия `667a12a1`, ручной `/compact` без текста на 123.7k, Opus 5 `high`, окно 1M.
Числа — из записи `compact_boundary` в транскрипте и из `session-cost.js`.

| Что | Значение |
|---|---|
| `trigger` | `manual` |
| `preTokens` → `postTokens` | 123 729 → 5 144 (4.2 % от сообщений) |
| `cumulativeDroppedTokens` | 118 585 |
| `durationMs` | 98 885 — полторы минуты ожидания |
| Сводка | 10 398 символов ≈ 4.7k токенов |
| `preservedSegment` / `preservedMessages` | head, anchor, tail — три сообщения хвоста перенесены **дословно**, не пересказом |
| `preCompactDiscoveredTools` | `WebFetch`, `WebSearch` — найденные по ходу инструменты переживают сжатие |
| Контекст по интерфейсу | 123.4k → 31.1k = база 21.8k + сводка 5.1k + впрыски хуков ≈4k |

Три вывода, которых не было в разборе по бинарю.

**Сохранённый хвост.** Сжатие — не только сводка: последние сообщения переносятся
дословно (`preservedSegment`). Поэтому свежая работа не теряет точности, а рвётся
именно середина сессии.

**Ход сжатия не пишется в транскрипт.** В `.jsonl` 46 записей с usage, а
`session-cost.js` насчитал 43 запроса; запроса в момент `compact_boundary` нет
вовсе. Значит цену сжатия наш замер не видит и никогда не увидит — её считают
руками по тарифу: чтение 123.4k из кэша $0.06 + выход 4.7k $0.12 ≈ **$0.18**.

**Перестройка кэша неполная.** Следующий ход после сжатия: запись 15 075 ($0.15)
при чтении 17 031 — префикс с системным промптом и инструментами остался в кэше,
переписывается только хвост. «Expected rebuild» стоит $0.15, а не цену всего окна.

Окупаемость: ход до сжатия стоил $0.091 (чтение 121k = $0.060), сразу после —
$0.043 (чтение 32k = $0.017). Разовые затраты $0.18 + $0.15 возвращаются
примерно за восемь ходов, и тем быстрее, чем длиннее была сессия.

Сохранность проверена вслепую: сразу после сжатия, без перечитывания файлов,
восстановились `keepRecent` 5 и порог 20 000, оба промаха заготовки
(`miss_custom_instructions`, `miss_hook`), разбор базы 21.7k по слагаемым и три
хеша коммитов ветки. Числа и хеши сводка держит.


## Почему порог 100k, а не 60k: полный расчёт

Расчёт 2026-09-16 на параметрах живого замера сессии `667a12a1`. Вопрос
владельца: если сжатие окупается, не выгоднее ли сжимать чаще — на 60–80k — и
держать контекст низким; и не увеличить ли размер сводки.

### Исходные величины

Тарифы Opus 5 1M обратным счётом из `session-cost.js` той же сессии:

| Статья | Токены | Доллары | Тариф |
|---|---|---|---|
| Чтение кэша | 3 010 365 | $1.51 | $0.502/M → `r` = 0.5e-6 |
| Запись кэша 1h | 123 680 | $1.24 | $10.03/M |
| Выход | 35 083 | $0.88 | $25.08/M |

Пол контекста `F` = 31k: база 21.8k (промпт 4.2 + инструменты 11.5 + память 4.6
+ навыки 1.4 + агенты 0.1) + сводка 5.1k (`postTokens` 5 144) + впрыски хуков
SessionStart ≈4k. Сходится с показом интерфейса 31.1k.

Скорость роста `G` — по приращениям контекста между запросами транскрипта:

| Отрезок | Ходов | Контекст | Средний прирост | Медиана | Максимум |
|---|---|---|---|---|---|
| До сжатия | 41 | 29.2k → 123.4k | 2.35k | 1.70k | 27.4k |
| После сжатия | 20 | 32.1k → 70.0k | 1.99k | 1.96k | 5.0k |

Медиана вдвое ниже среднего: рост идёт редкими крупными вбросами (максимум
27.4k — один результат инструмента), а не ровно. В расчёте `G` = 2.5k с
проверкой на 5k.

### Цена одного сжатия

По слагаемым, все три измерены:

| Слагаемое | Расчёт | Доллары |
|---|---|---|
| Перестройка кэша | 15 075 записи × $10/M | $0.151 |
| Выход сводки | 4 726 токенов × $25/M | $0.118 |
| Чтение при сжатии | 123 400 × $0.5/M | $0.062 |
| **Итого** | | **$0.331** |

Постоянная часть — 81 %, переменная (чтение) — 19 %. Отсюда
`K(T)` = 0.269 + `T` × 0.5e-6: сжать на 60k дешевле, чем на 123k, всего на
три цента. **Это и есть ответ на вопрос**: экономить, сжимая раньше, почти
не на чем, а платить фиксированные $0.27 придётся вдвое чаще.

### Цена хода: наблюдения

Разложение реальных ходов вокруг сжатия (запись 1h $10/M, чтение $0.5/M,
выход $25/M):

|---|---|---|---|---|

| 05:01:10 | 1 538 | 119 571 | 701 | $0.093 |

| — сжатие — | | | | ≈$0.331 |
| 05:05:33 | 15 075 | 17 031 | 1 724 | $0.203 (с перестройкой) |
| 05:05:48 | 2 263 | 32 106 | 171 | $0.043 |

| 05:06:40 | 1 358 | 38 782 | 1 076 | $0.060 |

Чтение на ход: $0.060 → $0.017. Окупаемость разового вложения:
0.331 ÷ 0.043 ≈ **8 ходов**.

### Модель

Контекст пилообразен: растёт от `F` до `T`, сбрасывается в `F`. Цена той части
хода, на которую влияет порог (чтение плюс размазанное сжатие):

    C(T) = (F + T)/2 × r  +  K(T) × G / (T − F)

Первое слагаемое — чтение среднего контекста цикла, второе — цена сжатия,
делённая на `N` = (`T` − `F`)/`G` ходов между сжатиями. Выход и запись кэша на
ход от порога не зависят (≈$0.03 на ход) и в модель не входят — проценты ниже
считаются от той части, которой порог управляет.

### Вывод оптимума

Пусть `x` = `T` − `F`. Пренебрегая зависимостью `K` от `T` (19 % суммы),
`K₀` = 0.269:

    C = (2F + x)/2 × r + K₀ × G / x
    dC/dx = r/2 − K₀ × G / x² = 0
    x = sqrt(2 × K₀ × G / r) = sqrt(2 × 0.269 × 2500 / 0.5e-6) = 51 720

То есть `T` ≈ 31k + 51.7k = **83k**. Численно, с учётом зависимости `K` от `T`,
на сетке 0.5k минимум приходится на **84.0k** ($0.04335 на ход).

Оптимум пропорционален `sqrt(K × G)` — это корень, а не прямая. Вчетверо более
дорогое сжатие двигает порог лишь вдвое. Отсюда плоское дно: ошибка в порядке
величины параметра стоит единиц процентов.

### Больший буфер сводки

Сводка вдвое длиннее (4.7k → 9.4k) поднимает пол до `F` = 36k и цену сжатия:

    K = 0.151 + 9 400 × 25e-6 + 90 000 × 0.5e-6 = $0.430
    N = (90 − 36)/2.5 = 21.6 хода
    C = (36 + 90)/2 × 0.5e-6 + 0.430/21.6 = 0.0315 + 0.0199 = $0.0514

Против $0.0435 — дороже на **18 %**. Перерасход $0.0079 на ход × 23.6 хода
цикла = $0.19 за цикл, то есть подробная сводка обязана экономить два-три хода
перечитывания за цикл ($0.06–0.09 каждый). На пакете L это неправдоподобно:
источник истины лежит в спеке, плане и журнале SDD, а не в сводке. Вдобавок
увеличить сводку бесплатно нельзя — ручная инструкция даёт
`miss_custom_instructions` и отменяет заготовку, а правило в CLAUDE.md смещает
фокус, но не объём.

### Неденежные доводы против частого сжатия

- 99 секунд простоя на каждое сжатие; при пороге 60k — каждые ~12 ходов.
- Сжимается уже сжатое: потери накапливаются, а дословно сохранённый хвост в
  замере оказался 364 символа — на него рассчитывать нельзя.
- Меньший запас под один большой результат инструмента: максимальный
  наблюдённый вброс 27.4k, при пороге 60k это почти половина рабочего окна.

### Вывод

Порог 100k остаётся. Настоящий рычаг — не порог, а скорость роста: при том же
пороге удвоение `G` с 2.5k до 5k удорожает ход с $0.0443 до $0.0558, то есть на
**26 %** — на порядок больше, чем даёт любая перенастройка порога. Всё, что
замедляет рост (брифы сабагентам файлами, вывод больше 12k в файл, не
перечитывать планы), экономит сильнее, чем сжимать чаще.

Границы расчёта: модель линейна по росту, берёт сводку одного размера на любом
пороге и одну измеренную цену сжатия. Если на 60k сводка выйдет заметно короче,
низкий порог подтянется к уровню 80k, но не обгонит его; вывод устойчив в обе
стороны. Проверять при смене тарифов, при изменении базы контекста (пол `F`
входит в формулу дважды) и после первого замера на живом пакете L.

### Оптимум функции и порог правила — разные ответы

84k — минимум модели для одного режима (рост 2.5k на ход). Порог правила — 100k,
и это не небрежность. При росте 5k на ход оптимум уезжает к 104k, и порядок
меняется на обратный:

| Порог | Лёгкая сессия (G=2.5k) | Тяжёлая (G=5k) | Сумма |
|---|---|---|---|
| 84k | $0.0434 | $0.0581 | $0.1015 |
| 100k | $0.0443 | $0.0558 | **$0.1001** |

100k проигрывает 2 % там, где 84k лучше, и выигрывает 4 % там, где хуже: на
смеси режимов дешевле именно 100k. Плюс цена самой перемены — правка
`context-budget.ps1`, семь тестов, деплой, а деплой переписывает кэш всех
открытых сессий. Читающему «оптимум 84k» менять правило не нужно.

## Как запускать сжатие автоматически

Разбор бинаря 2.1.269 от 2026-09-16; **замером не подтверждено**, проверять по
плану в конце раздела.

### Штатный порог настраивается

Главное, чего не было в первом разборе: порог автосжатия — не константа окна.

| Рычаг | Что делает |
|---|---|
| `/autocompact [auto\|<tokens>]` | команда `type:"local"`, `immediate`, описание: «Set how full the context gets before auto-summarizing» |
| `autoCompactWindow` | та же величина в `settings.json` |
| `CLAUDE_CODE_AUTO_COMPACT_WINDOW` | env, **старше настройки**: «is set and takes precedence. Unset it to change this setting» |
| `CLAUDE_AUTOCOMPACT_PCT_OVERRIDE` | опускает порог ещё ниже долей |
| `DISABLE_AUTO_COMPACT`, `DISABLE_COMPACT` | выключают; второй убивает и ручной `/compact` |

Порог по схеме телеметрии: `effective_window` минус буфер сводки, ещё ниже при
`PCT_OVERRIDE`. Поле `enforced` — «будет ли сжатие действительно запущено на
`threshold`»; в бинаре есть сообщение «limit isn't enforced for <модель>, so
this session can grow past it. To enforce it, set
CLAUDE_CODE_AUTO_COMPACT_WINDOW», то есть на большом окне ограничение может не
применяться, пока его не задать явно. Значение парсится как `auto`, `100k`,
`1M` или число.

Отсюда рабочая связка для бюджета 100k: задать окно так, чтобы порог лёг куда
нужно, и автосжатие начнёт срабатывать само, без хука и без вопроса владельцу.
Величина буфера сводки при малом окне из кода не читается — в интерфейсе на
окне 1M он показан как 33.0k; пропорционален он окну или постоянен, **надо
измерять**.

### Чего сделать нельзя

**Модель не может сжать сама.** `compact` объявлен `type:"local"`, а инструмент
`SlashCommand` пускает к модели только `type==="prompt"` (плюс
`!disableModelInvocation`). Никакой промпт, правило или напоминание этого не
обходит: команду набирает владелец либо запускает штатный автомат.

**PreCompact-хук не запускает сжатие.** Он модифицирует уже начатое и вдобавок
отменяет заготовку сводки (`miss_hook`). Как средство автозапуска бесполезен.

**Headless — отдельная история.** У команды `supportsNonInteractive:!0`, то есть
`claude -p "/compact"` работает в неинтерактивном прогоне. Для скриптов годится,
для живой сессии нет.

### Три варианта и что выбрать

| Вариант | Цена хода | Кто решает | Минус |
|---|---|---|---|
| Штатный автомат (`/autocompact`) | сжатие без лишнего хода | никто, срабатывает само | рвёт работу в произвольный момент; владелец теряет точку решения |
| Хук с вопросом на 100k (сейчас) | один ход на вопрос (~$0.09 при 120k) плюс ожидание ответа | владелец | вопрос может висеть часами |
| Блокирующий хук на 150k (сейчас) | ноль, пока не упёрлись | владелец, принудительно | поздно: ход на 150k уже стоит $0.075 чтения |

Разумная связка — не «или», а слои: вопрос на 100k оставить (владелец решает в
удобный момент), а штатный автомат поставить страховкой выше, чтобы контекст не
убежал, если ответа нет. Тогда блокирующий предел остаётся последней чертой.

### План проверки

1. `/autocompact 133000`, затем `/context`: прочитать показанный буфер
   автосжатия и посчитать фактический порог.
2. Убедиться, что значение записалось в `settings.json` как `autoCompactWindow`
   и что `CLAUDE_CODE_AUTO_COMPACT_WINDOW` не задан (иначе он старше).
3. Довести сессию до порога и замерить: сработало ли, ушло ли событие
   `compact_auto`, взялась ли заготовка (`precomputeReuse` вместо
   `miss_*`) — по `durationMs` в `compact_boundary`, не на глаз.
4. Результат — строкой в `docs/costs.md` и правкой порога в
   `global/CLAUDE.md`, если автомат окажется надёжнее вопроса.

## Живой замер автосжатия 2026-09-16

Проверка по плану выше, в той же сессии. Владелец набрал `/autocompact 133000`;
значение легло в `~/.claude/settings.json` (`"autoCompactWindow": 133000`),

### Порог — это окно минус постоянный буфер

| Окно | Буфер автосжатия в `/context` | Порог |
|---|---|---|
| 1M (по умолчанию) | 33.0k | 967k, недостижим |

окно T + 33k.

Сработало не в момент пересечения, а на следующем ходу: `preTokens` 104 376

### Протокол чистого прогона

Слепая проверка на этом куске больше невозможна — материал в контексте.
Повторить на следующем автосжатии, не подгоняя порог:

1. Из транскрипта взять две соседние записи `compact_boundary` и номера
   строк между ними — это отброшенный кусок.
2. Вытопить его в текст скриптом: из каждой записи взять `message.role`,
   блоки `text`, имена и аргументы `tool_use`, текст `tool_result`;
   `thinking` выбросить, длинное обрезать с пометкой. Транскрипт в
   контекст водителя не попадает ни на одном шаге. Если экзамен станет
   регулярным, скрипт переезжает в `scripts/` с описанием в
   `docs/scripts.md`.
3. Агент-экзаменатор (Sonnet 5) читает файл через `Bash`, не `Read`:
   на `Read` стоит `read-gate`. Возвращает **только** вопросы —
   формулировка запрета по `docs/agent-prompts.md`.
4. Ответы водителя уходят тому же агенту через `SendMessage`: эталоны у
   него в контексте, 54k второй раз не читаются.
5. Оценка по типам фактов — числа, имена, принятые решения, отвергнутые
   варианты с причиной отказа. Ожидание по этому замеру: первыми теряются
   имена и числа закрытых тем, дольше живут решения открытой.
